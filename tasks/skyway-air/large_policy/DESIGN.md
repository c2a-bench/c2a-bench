# skyway-arch large policy: design sheet

Goal: make runtime retrieval necessary in skyway-arch without changing or adding tickets.

1. Add a large body of Skyway support policy in areas no existing rule or ticket touches.
2. Cap every bot model call at 12,000 tokens (`prompt_cap_tokens` on every case; counted as characters / 4,
   messages + tool definitions), and state the cap in the instructions.

Condensed, the new knowledge must be 24-36k tokens (2-3x the cap), so no bot can carry it all; each ticket still
needs only the rules it needs today (the existing ~32 rules condense to ~2.4k tokens).

Scope: skyway-arch only. New docs go in at stage 0, and the new policy also changes in stages 1-5 (see "Stages
1-5"), so later stages add docs to it too.

## Independence: what the new policy must never touch

Every existing ticket must keep its exact expected answer, and no new doc may compete with an existing rule in
retrieval. So the new policy never mentions or decides:

| Excluded | Because of |
|---|---|
| refunds, travel credit, compensation, reimbursements, approvals, any payment | R2-R5, R9-R13, R15, R16, R20, R22, R26, R29, R32 |
| delays, cancellations, retimes, missed connections, overnights, hotels, meals, ground transport | R1, R2, R9, R10, R12, R23, R26, R27 |
| bags of any kind: delayed, damaged, claims, deadlines, wear | R13-R15 |
| booking changes, fees, fare differences, Skyway Miles **tiers** (Silver, Gold) | R7, R8 |
| pets, children, minors, family seating | R6, R30, R31 |
| wheelchairs, assistance, accessibility | R22 |
| travel agencies, travel managers, company accounts, who may act on a booking | R4, R17, R24 |
| illness, doctors, medical, injury, legal, discrimination | R19, R25 |
| dangerous goods, batteries, what may be carried on board | `handoff-03` expects not_covered (R19): a new rule covering it would change its answer |
| following up earlier tickets, failed payments, confirmation ids | R28, R29, R32 |

Actions the new rules may use: the reply to the customer, category `other`, new labels (e.g. `privacy-request`,
`lost-item-logged`, `docs-check`), ticket comments. **No payment endpoint, no booking change, no handoff**
(handoff reasons belong to R19).

Hidden-case label checks list only the existing labels, so new labels cannot fail an existing ticket; to verify.

## Areas and size

The full list is in `PLAN.md`, generated by `plan.py` (which also runs the excluded-term check: 0 hits).

| Area | Rules | Tables |
|---|---|---|
| Check-in and boarding | 19 (+1 in stage 1) | per station x season: check-in cut-offs, counters open, gate close |
| Travel documents | 12 (+1 in stage 4) | per country (60): passport validity, entry permit, upload lead time, onward travel, residence card, temporary passports |
| Accounts, privacy and the app | 18 (+1 in stage 2) | none |
| Airport facilities | 10 (+1 in stage 5) | per station x season: lounge and station-office hours, Document Check desk hours; fixed: lounge and parking partner, terminal, zone, kiosks, phone, quiet room, smoking, water |
| Charter, cargo, media and other enquiries | 13 (+1 in stage 3) | none |
| **Total** | **71** | **185 stations (68 international), 60 countries** |

Size: ~75k tokens as written; condensed floor ~17k tokens (rules as their sentences, tables as dense rows). With a
lean bot's own ~5k prompt that is ~22k, against the 12k cap. The two reference bots confirm it.

Dropped after review against the existing rules (they share a topic with a tested rule): Skyway Miles (R8), items
left on board (delayed bags, R13-R15), seat requests and sitting together (R30), early boarding (R22), email-match
and acting for someone else (R17, R24), compliments about staff (R16), aircraft changes (disruptions).

The station tables leave out the 17 airports the tickets use (ATL, BNA, BOS, DEN, DFW, HOU, IAH, JFK, LAX, LGA, MCO,
MIA, ORD, PHX, RDU, SEA, SJU) and their cities, so no station page competes with a ticket's rule docs.

## Docs

- ~300 stage-0 docs. Rule pages and Slack threads go through `tools/doc-gen` (planned docs, step 7),
  checked with `check_docs.py`. Station and country pages are mostly tables (25-30 values each): their tables are
  written by script, word for word from plan.py, and the generator writes only the surrounding text, so no value
  can come out wrong.
- Same mix as the corpus: Confluence policy and playbook pages, Slack threads that carry or update a rule, the same
  messy appearances (fragmented, outdated versions marked as replaced, drafts), names and dates like the existing
  rule pages.
- Where they go: new subfolders in the existing spaces (e.g. customer-policies/check-in-and-boarding,
  customer-policies/travel-documents, support-playbooks/accounts-and-privacy) and the matching Slack channels.

## Stages 1-5

Each stage also changes the new (untested) policy, the way a real policy base moves, mixed in with the tested rule
changes and the ordinary churn of ../scripts/blend_stage_churn.py. No ticket changes: every change here is in an area no ticket uses.

| Change per stage | Examples | Appears as |
|---|---|---|
| Values updated | a station's check-in cut-off, a lounge's hours, a country's passport-validity rule, a partner's earning rate | patched docs (edited) |
| New rules | a new privacy-request step, a new destination, a station opening | new Confluence pages and Slack threads (added) |
| Rules retired | a partner leaves, a station closes | the page marked replaced, or removed (removed) |
| Drafts and proposals | "proposed winter cut-offs", "draft: new ID check" | new docs that look like changes but are not in force (added) |
| Messy appearances | the same patterns the tested changes use: conflicting, fragmented, incomplete, noisy | as above |

Why: today a diff of a stage's added docs is rich in tested rule docs (stage 1: 46 of 156 added docs, lift 11.7;
blend_stage_churn.py dropped its planned ordinary new docs). Untested policy additions look exactly like rule additions, so they
dilute that signal far better than ordinary background docs, and they also test whether the bot keeps the whole
policy base current.

Size per stage (leak check 3 on main, 2026-11-12; extra added docs needed for lift <= 2.5, i.e. some margin under
the 3.0 bar; computed with each stage's base rule share, extras accumulating):

| Stage | Added today | Rule docs among them | Lift | Extra added docs (lift 3.0 / 2.5) |
|---|---|---|---|---|
| 1 | 156 | 46 | 11.7 | 482 / 619 |
| 2 | 115 | 37 | 11.2 | 356 / 455 |
| 3 | 77 | 25 | 10.5 | 227 / 290 |
| 4 | 56 | 18 | 9.8 | 154 / 197 |
| 5 | 52 | 17 | 9.5 | 140 / 179 |
| **Total** | | | | **~1,360 / ~1,740** |

That is more than untested-policy changes can plausibly supply (~185 rules at stage 0). So each stage's extras are
a mix: ~60-100 untested-policy docs (new rules, updates, drafts, Slack threads about them), which carry the
look-alike weight, and the rest ordinary new background docs (generator step 9, as the stage-0 background was
made). The added docs must also pass check 3's inner filters (name, size, title, document type), so the extras
follow the rule docs' own shapes, not just their count.

Guards, as for stage 0: no new or changed doc touches an excluded topic; every stage's existing tickets keep their
exact expected answers (`solvability_review.py` per stage with that stage's old + new rules); `leak_check.py` passes
check 3 for every stage; `package_stages.py --replay` reproduces each stage.

## Checks before release

| Check | Must show |
|---|---|
| Key-term filter on every new doc | no excluded term (table above, plus `AVOID` in add_policy_lookalikes.py) |
| Reviewer pass: each new rule against all 32 existing rules | no shared situation, money type or decision |
| Retrieval per existing ticket (BM25 and embeddings over the full corpus) | the ticket's rule docs rank no worse than before |
| `solvability_review.py` with old + new rules | every existing ticket keeps its exact expected answer |
| `check_docs.py`, `leak_check.py`, `split_check.py` | values present; no cheap filter separates tested from untested rules |
| Lookup bot under the 12k cap | about today's score: the cap is fair |
| Load-everything bot under the 12k cap | does not fit: retrieval is forced |

## Packaging

The published Skyway Air task already has it. `add_large_policy.py` (next to this file) is the step that added it to the task built by `../scripts`: the docs, the cap on every case, the instruction lines and the four practice examples.

The knowledge no longer fits in one call next to the tested rules, so a load-everything bot has to select per ticket.
A per-call cap cannot stop it reading the tables across extra calls; what remains is the cost in calls and time.
